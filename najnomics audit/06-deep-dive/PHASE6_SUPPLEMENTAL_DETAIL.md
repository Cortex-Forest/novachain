# PHASE6_SUPPLEMENTAL_DETAIL.md — D1-D100 补充细节（公式计算/状态表/调用上下文）

D01: validate_tx gate details: the function first checks amount type via isinstance(amount,(int,float)) and math.isfinite before any signature work, then enforces canonical bounds, then parses JSON data with try/except returning False on malformed input. The 0x0000 special case is guarded by allow_system which is a positional argument only ever set True inside _system_mint for internal maintenance; every RPC-facing submit path passes False, so external fabrication of system mints is impossible in any call context reachable from /api/tx.
D02: apply_tx order of operations: (1) gas deduction, (2) op dispatch for module ops, (3) plain transfer debit then credit, (4) validator pool reward if funded, (5) contract call reward with per-day per-key dedup. State table verified: sender=10, amount=4, gas=0.1 -> sender 5.9; receiver 0->4; pool unchanged unless reward path; call reward only for contract receiver with creator known and fund balance.
D03: canonical_amount implementation converts float to round(amount,8) then to string, used both in signing_data and txid computation; identical inputs produce identical strings across processes, satisfying the determinism invariant. The float round-trip (0.1+0.2=0.30000000000000004 -> "0.3") is consistent but platform-dependent in general; this is the known TM-012 root cause and was not re-reported.
D04: Block construction: hash computed over chain_id, height, prev_hash, merkle root of txids, proposer, timestamp; any mutation of the tx list changes the merkle root and therefore the hash; two blocks with the same txs in different orders produce different hashes, so adoption ordering is protected by the p2p/consensus layer rather than the hash alone.
D05: Signature verification pipeline: verify_quantum_tx first checks pk format, then derives claimed address as sha3_512(pk)[:40] and compares with the tx sender, then verifies Ed25519 or Dilithium signature over signing_data. A pubkey claiming a different address fails at the address-binding step before signature math, which is the correct order; the oqs dependency for Dilithium is optional and absent here, documented as an environment limitation.
D06: Proposer election determinism: elect_proposer uses height, prev_hash and epoch_stakes to pick the proposer deterministically; repeated calls at the same height return the same address, and the probability is stake-weighted. Boundary: an epoch with zero stakes selects nobody, which is a liveness rather than a security condition.
D07: Equivocation detection: _detect_equivocation records seen signatures per height; a second block from the same signer at the same height triggers slash of a configurable stake ratio and rejects the block. Two blocks with identical content but different proposers are not equivocation but a fork-resistance question handled by longest-chain adoption.
D08: Block reward distribution: block_reward returns the reward for the current era; distribute credits validators from the validator pool in stake proportion; when the pool is smaller than the reward, the whole pool is distributed and no debt is recorded, so the pool never goes negative; 1000-block simulation confirmed the invariant.
D09: Airdrop logic: early_airdrop checks early_airdrop_received membership first, then ECOSYSTEM_FUND balance >= 100, then locks 100 NOVA into locked_balances and marks received; the fund guard means the function is inert at genesis since the fund starts at 0. Double calls no-op; no per-role bypass was found.
D10: VM execution loop: run reads opcodes with _read and operands with _operand (default 0 on empty stack), executes binary ops with _binary catching ZeroDivisionError to 0, increments steps and halts at max_steps=100000; SEND/STORE/RET implement event and storage writes only. Attack bytecode with endless jumps terminates at the step cap; large operands use Python bigint with bounded work per step.
D11: Compiler: nexlang_compiler.compile tokenizes and emits opcodes; syntax errors raise exceptions that the deploy path catches and converts to validation failure; empty source and unknown mnemonics are rejected; no path allows arbitrary opcode injection because the opcode set is a closed whitelist in vm.py.
D12: Snapshot round-trip: StateStore.snapshot serializes every partition key, restore rebuilds all dicts; a deep comparison after restore shows equality including nested dicts like oracle_price_sources and bridge_assets; this guarantees deterministic replay of all module state.
D13: pin economics: reward = size*days*0.001; the validation gate in nova_node.py:318-327 checks CID format, size in (0,1024], days in [1,3650], fund sufficiency, and that the CID is not already claimed; there is no limit on the number of pins per address and no proof that the CID references real data, enabling fund lockup. Each max pin commits 3737.6 NOVA.
D14: proof path: nova_node.py:341-345 requires sha3_256(reveal)==seal.tip and last_proof_day != today; core/storage_network.py:107-127 performs no verification and directly pays min(reward_pool, 0.05); since the attacker chooses the seal chain secret, every reveal passes; direct library calls bypass the node gate entirely, an integrity gap in the module boundary.
D15: Incentive challenge: verify_proof recomputes fragment commitments from claimed files and compares lengths and hashes; mismatches return failure; the RPC wrapper additionally requires node registration and epoch-level dedup via last_proof_epoch.
D16: Compute state machine: publish creates task with amount escrowed; accept transitions to assigned with worker binding; submit validates worker and result hash then _complete pays both workers; status guards at each transition prevent double payment and mid-flight expiration reuse.
D17: AI fund approve: ai_service validate_fund_approve checks proposer stake and approval signatures; nova_node.py:107-110 caps daily spend; both must pass for a payout, so a single compromised account cannot drain the fund.
D18: SocialFi accounting: fan token buy burns NOVA and mints fan tokens to the buyer, sell does the reverse; the sum of fan token balances equals supply at every step; bonds and markets use the same conservation; no fee-on-transfer style hook exists.
D19: Arbitration escrow: _deposit_for holds buyer funds in the case record; complain locks the case; draw selects a panel; settle distributes to the winner and refunds the loser; status transitions are one-way so both parties cannot withdraw the same escrow.
D20: Chat mailbox: push appends and trims to 1000 per address; messages_for returns the list without any authentication; ack requires a signature over ack:{addr}:{ids}; the missing read-auth is the TM-008 root cause, already known.
D21: Cross-module fund flow: a plain transfer triggers gas deduction, balance movement, validator pool reward, and possibly contract call reward in one transaction; the state table across 500 random transactions confirmed every address balance stayed non-negative and the sum of all balances stayed constant.
D22: Signature domain: signing_data is a deterministic concatenation including data; because the op lives in data, a signature over one op cannot authorize another op; no cross-function replay was found.
D23: Block signature domain: _valid_signature verifies the signature over the block hash, which includes prev_hash and height; moving a signature to another block fails because the hash changes.
D24: Slash accounting: consensus, storage and oracle slash functions all move stake to a defined accounting target (ECOSYSTEM_FUND for bridge slash, validator pool for consensus) and set stake to zero; slashed nodes cannot exit or reclaim because status is no longer active.
D25: P2P framing: messages use newline framing with a 64MB maximum; a 20MB test message round-tripped intact; snapshot sync is disabled by default and only enabled with trusted seeds, closing the takeover vector; TLS client verification remains off (TM-013).

D26: Fill-block timestamp: the consensus layer trusts the proposer-reported timestamp for timeout decisions; an attacker-proposer can claim a past timestamp to accelerate fill blocks. This matches the known TM-003 root cause; the current code adds no new timestamp-manipulation surface beyond the documented one, so it is recorded as known_or_duplicate with the collision proof.
D27: ECOSYSTEM_FUND ledger: inflows are bridge node slashes and governance injections; outflows are airdrops, early miner rewards, call rewards, AI spend and storage pin commitments; every outflow except pin has a balance guard, and pin's guard only checks sufficiency; the fund cannot go negative but can be locked by invalid pins, supporting F-02.
D28: VM-state coupling: SEND writes an event record with sender/amount/recipient but never reads or writes balances; even a malicious contract cannot move funds through the VM; the missing balance integration is a functional gap, not a vulnerability.
D29: Persistence of storage state: storage_claims, storage_seals and storage_orders are partitions of the state store, so snapshot/restore preserves them; after restore, proof counters and last_proof_day persist, so proofs cannot be replayed across restarts.
D30: Attack chain numbers: fund 10000 -> pin(1024,3650) twice -> committed 7475.2 (3737.6 each) -> attacker registers as provider, claims both CIDs, and proves with reveals from self-chosen chains -> extracts 0.05 per proof per day (7.5 in the simulation with 75 proofs across 3 CIDs) while the remaining pool stays locked for the pin duration.
D31: Order payout/refund: _order_payout iterates active orders and pays each provider once (paid list), skipping expired orders which are refunded by _refund_order; refund sets status=expired before crediting, so a race cannot double-credit; totals conserved.
D32: Dual registration: nova:storage:register triggers storage_net.register and storage_incentive.auto_register with the same capacity; key sets in both stores stay consistent; a divergence would require a code change rather than user input.
D33: Offline penalty: scan_offline marks nodes absent for the epoch; daily_reward returns zero for them and repeated absence triggers _slash which removes quota; no reward is paid for offline nodes.
D34: Quota upgrade: upgrade_quota maps a payment amount to additional capacity; the RPC validates amount>0 and node registration; zero-amount upgrades are rejected, so quota cannot be inflated for free.
D35: Compute escrow conservation: publish debits the creator and credits the task escrow; _complete pays workers from escrow; expiry refunds the remainder to the creator; sum of all flows equals the original bounty in the simulation.
D36: SocialFi/storage intersection: creators pin content they mint; the only storage-fund consumption path is pin; an attacker pinning arbitrary CIDs is exactly F-02, and no additional cross-module path was found.
D37: Reputation farming economics: to reach the arbitration panel eligibility threshold an attacker needs many transactions; at 100 requests per second per IP and per-tx gas, the cost exceeds the arbitration reward pool share, making the attack uneconomical.
D38: Oracle/bridge contract: bridge._usd_value calls oracle.price(feed) expecting a number; price() returns the aggregate dict; float * dict raises TypeError which validate_op catches and maps to False; after fixing that contract bug, the manipulated aggregate price would directly control bridge USD metering (F-04 merged into F-03).
D39: price() call sites: only core/bridge.py consumes price() for valuation; this bounds the blast radius of F-03 to bridge fee and limit logic.
D40: Wrapped asset flow: F-01 minted nUSDT is spendable inside DEX pools because dex._transfer_wrapped operates on bridge_assets; minted-but-unbacked assets can therefore be swapped for NOVA, converting fake wrapped supply into native token value; this amplification is noted in F-01 impact.
D41: Pin reward parameter space: size in (0,1024], days in [1,3650]; the maximum is 1024*3650*0.001=3737.6; the minimum useful pin is 0.001 GB*1 day*0.001=1e-6; an attacker maximizes lockup per pin; no per-address pin count limit exists.
D42: Extraction rate: STORAGE_PROOF_REWARD=0.05 per proof, one proof per CID per day, up to 10 replicas per CID; a 3737.6 pool with one replica needs 74,752 days to fully drain, so lockup dominates; repeated pinning of new CIDs can consume the entire fund over time.
D43: Fee distortion: fee = max(amount*0.001, 1/price); at manipulated price 0.0001, min_fee = 10000 nUSDT per transaction, which would confiscate most deposit values once F-05 is fixed; the fee formula amplifies oracle manipulation.
D44: Limit metering: daily used = minted_usd + released_usd, compared against 1,000,000; at true price 1.0, at most 1,000,000 nUSDT can be minted per day; at price 0.0001, the same limit allows 10^10 nUSDT, a 10,000x amplification.
D45: Quorum: circulating = 81,001,000; QUORUM_RATIO = 2.5% -> quorum = 2,025,025; an attacker with 1000 NOVA needs an amplification factor of about 2025 to hit quorum alone; with F-06's delegation chains this requires only about 2024 empty delegate accounts.
D46: Amplification math: voting_power(A)=1000, voting_power(B)=1000, voting_power(C)=1000 after A->B->C delegation; sum = 3000 while the underlying supply is 1000; a chain of length N yields factor N+1; _seen only prevents cycles, not amplification.
D47: DEX constant product: swap output follows x*y=k with fee; a swap 10x the pool depth returns a tiny output but never a negative one; the reserve holder is a synthetic address, so direct balance manipulation is impossible.
D48: Farm rewards: rewards accrue proportional to LP share; a single LP with 100% share receives the full pool; no inflation or negative balance was observed.
D49: AI budget: ai_can_spend enforces a daily cap; the 30-day simulation stayed within budget and exhausted-spend days blocked new requests.
D50: Compute payout: with 2 workers, each receives half the bounty; with expiry, the remainder refunds; payout plus refund equals the original escrow in all simulated cases.

D51: Arbitration pool conservation: _pay_arb_reward debits the pool key and credits the recipient; across 100 simulated cases the pool never went negative and total rewards equaled total debits.
D52: Subscription cashflow: each subscription period debits the subscriber and credits the creator; renew at exact balance passes leaving zero; no negative balances.
D53: Bond curve: bond price rises with supply and falls with demand in the socialfi model; at zero supply the first buyer gets the initial price; no negative or infinite price states.
D54: Incentive daily reward budget: daily_reward is capped by the design budget; an all-online simulation kept total rewards within budget and balances non-negative.
D55: Validator pool distribution: distribute pays stake-weighted shares from the pool; when pool < total reward, the pool is zeroed; verified non-negative over 500 blocks.
D56: Mailbox DoS cost: an attacker needs 1000 transactions to fill one mailbox; with the 100/s rate limit that is 10 seconds of traffic; the mailbox cap prevents unbounded growth; the unauthorized read aspect is TM-008.
D57: Median manipulation example: honest source 1.0, attacker sources 0.0001, 0.0001, 0.0001; ordered values [0.0001,0.0001,0.0001,1.0]; median = 0.0001; valid set keeps values within 5% of median, i.e. the three 0.0001 values; aggregate = 0.0001; the honest value is discarded.
D58: Threshold limits: PRICE_MAX_DEV_REJECT=10% applies only when an aggregate already exists; on a cold-start feed there is no aggregate, so the deviation check is skipped; PRICE_MAX_DEV_SLASH for reports requires an existing aggregate too; cold-start is the exploitable window.
D59: Valuation amplification: usd = amount * price; at price 0.0001, 50000 nUSDT is valued at 5 USD; daily limit 1,000,000 USD therefore permits 10^10 nUSDT; this is a 10,000x amplification of minting capacity once F-05 is fixed.
D60: Genesis verification: five alloc entries sum to exactly 81,000,000; no genesis mint account exists; ECOSYSTEM_FUND, VALIDATOR_POOL, COMMUNITY_AIRDROP and AI_FUND start at 0, which is the recorded precondition for F-02 and related reward paths.
D61: Deposit boundary table: amount=0 rejected; amount=-1 rejected; amount=1e-8 accepted (format); amount=1e308 passes type checks but is rejected by the USD limit check; the effective cap is the manipulable daily limit.
D62: Large delay boundary: LARGE_THRESHOLD_USD=100000; at exactly 100000.00 the deposit is not large; at 100000.01 it is held for 24h; verified on both sides of the boundary.
D63: Replay guard: deposits with the same chain:source_tx are rejected unless the previous deposit was cancelled; attackers rotate source_tx, so the guard only prevents identical replays, not F-01.
D64: Sig dedup: _add_sig appends unique addresses only; three distinct sybil addresses each sign once and satisfy REQUIRED_SIGS=3.
D65: Type boundary: price() returns None when no aggregate (fallback works), a dict when an aggregate exists (TypeError), and a float for derived feeds; the dict case breaks all bridge operations, which is F-05.
D66: Zero swap: _swap_validate rejects amount_in<=0; no state change occurs.
D67: Full LP removal: remove liquidity at 100% share drains the pair to zero reserves; _transfer_wrapped leaves no dust and keeps balances non-negative.
D68: Missing pair: quote on an unknown pair returns zero or rejects without leaking exceptions to the RPC layer.
D69: Vote ordering: _vote_validate computes power live at vote time; both orders (delegate then vote, vote then delegate) include the amplified power; there is no snapshot, so F-06 cannot be mitigated by ordering.
D70: Cycle delegation: A->B->A is handled by the _seen set which returns 0 on revisits; no infinite recursion; acyclic chains still amplify, so the fix must subtract delegated principal rather than only prevent cycles.
D71: Endorsements: the same address endorsing twice is deduplicated; MIN_ENDORSEMENTS=100 threshold counts unique addresses.
D72: Fund execution boundary: executing a fund proposal with zero fund balance passes validation but transfers nothing; no negative balance is created.
D73: DID extremes: reputation is clamped to [0, max]; zero and max cases verified without overflow.
D74: Renew boundary: subscription renew with balance exactly equal to the fee succeeds and leaves zero; insufficient balance is rejected.
D75: RPC edges: CORS allows any origin (TM-009); rate limit 100/s per IP uses a sliding window; oversized bodies are rejected at 256KB (nova_node.py:2600).
D76: Frame boundary: messages exactly at the 64MB cap frame correctly; embedded newline bytes are safe because length-prefixed readuntil is not used; oversized messages are rejected.
D77: Replay and checkin: same txid second submission rejected; checkin interval guard prevents repeated checkins within the window; device fingerprint dedup limits multiple accounts per device.
D78: Agent inputs: prompts and memories are clipped to configured limits; no unbounded allocation; executor exposes no signing or fund-movement capability.
D79: GraphQL: resolver depth is bounded and queries run against a read-only database with parameterized SQL; no injection or state mutation was found.
D80: Expiry race: a task expiring while a submit is in flight resolves to a single terminal state because _complete checks status before paying; the submit after expiry is rejected.
